1. Architecture and frame flow

Puppy3D is a GTK desktop editor that owns an EngineScene, an InputService, and an optional LuaRuntime. The editor assembles and connects the UI; the scene owns editable objects and rendering data; helper modules load or save file formats.

GTK window and callbacks (main.cpp)
        |                         |
        | UI changes               | timer (~16 ms)
        v                         v
    EngineScene <--- LuaRuntime    InputService
        |                              ^
        |                              |
        +---- GlbImporter              +---- GTK key/mouse events
        +---- Rendering/EngineVarMeshRenderer
        |
        +---- SceneDocument (XML read/write)
        |
        +---- OpenGL calls in GtkGLArea render callback
  1. main() starts GTK, initializes the input and audio subsystems, creates the Lua runtime, discovers res/, and builds the window.
  2. GTK's realize signal makes the OpenGL context current and initializes the engine's GPU objects.
  3. A GLib timer runs approximately every 16 ms. onEngineTick() polls controllers, measures elapsed time, updates Lua and model animations, clears per-frame input edges, and queues a redraw.
  4. GTK invokes onOpenGlRender() with a current context. The callback asks EngineScene::render() to draw the grid, cubes, and models.
  5. GTK input signals forward key and mouse state into InputService. Lua reads that state when its update(delta_time) function is called.

Important ownership rule: OpenGL handles are tied to a current GL context. Initialize them after the GtkGLArea is realized, render only in its render callback, and release them while that context is current during window shutdown.

3. Editor and GTK 3

main.cpp uses GTK's C API from C++. The private Editor struct is the shared application state passed to callbacks as gpointer. It contains widget pointers, file paths, dirty/editable flags, audio state, and the scene/input/Lua objects.

How GTK is put together

  • buildWindow() creates the window, toolbar, split panes, resource tree, notebook tabs, 3D area, properties panel, scene outliner, and inspector controls.
  • g_signal_connect() wires widget signals such as clicked, changed, row-activated, realize, and render to C++ functions.
  • GTK owns the event loop. Callbacks should update state/widgets and return promptly; the application does not create its own UI thread.
  • onTreeSelectionChanged() updates the selected resource and properties. Double-clicking a folder expands it, a GLB imports it, and other files open in the editor.
  • openFile() checks that the target is a regular file, enforces an 8 MiB size limit, reads bytes, and marks binary or invalid UTF-8 files as read-only. saveCurrent()/saveAs() write editable text and manage dirty state.
  • The scene outliner and inspector callbacks select objects and route edits to EngineScene. A guard flag prevents programmatic widget updates from being mistaken for user edits.
  • showError() presents GTK error dialogs; setStatus() updates the status bar.

GTK callback pattern

For a new button, create it during buildWindow(), connect its signal, and write a callback with GTK's expected signature. Keep the state change in the callback and refresh the UI explicitly.

void onResetClicked(GtkButton*, gpointer userData)
{
    Editor& editor = *static_cast<Editor*>(userData);
    editor.scene.clear();
    refreshSceneOutliner(editor, 0);
    gtk_gl_area_queue_render(GTK_GL_AREA(editor.glArea));
}

// In buildWindow(), alongside the other toolbar buttons:
g_signal_connect(button, "clicked", G_CALLBACK(onResetClicked), &editor);

This is a schematic extension example: use the existing makeToolButton() helper in main.cpp when adding a normal toolbar button, and ensure callbacks are declared before their use in buildWindow().

4. Engine data and scene API

Engine.h defines plain data types shared by the importer, renderer, Lua bindings, and scene-file code:

  • EngineVertex: one 3D position, normal, and 2D texture coordinate.
  • EngineTexture: decoded RGBA pixels and dimensions, plus a GPU texture handle once uploaded.
  • EngineMesh: mesh vertices/indices, base-color material, optional texture, associated glTF node, base node transform, and OpenGL VAO/VBO/IBO handles.
  • EngineModelNode: imported node parentage and either a matrix or translation/quaternion/scale transform.
  • EngineAnimationSampler, EngineAnimationChannel, and EngineAnimationClip: keyframe inputs, outputs, interpolation mode, target node/property, and clip duration.
  • EngineObject: scene-visible name, position, Euler rotation in degrees, scale, color, and model/source metadata.
  • EngineModelInstance: an object's imported model payload and its selected clip, playback time, and playing state.

EngineScene owns the object vector, imported model instances, cube/grid geometry, shader, and retired GPU meshes. Object IDs are one-based vector positions: the constructor seeds a cube, and addCube() returns the new object count. The setter methods return false for an invalid object ID; color is clamped to the range 0..1.

Method groupMethodsPurpose
ObjectsaddCube, addPolygon, setCubeVertex, pickObject, setPosition, setRotation, setScale, setColor, setObjectName, objectCount, object, clearCreate, inspect, modify, select, and remove scene contents.
Models and clipsimportGlb, animationCount, animationName, animationDuration, activeAnimation, animationTime, setAnimation, setAnimationPlaying, setAnimationTime, updateAnimationsAttach imported models and manage animation selection / playback.

When adding an engine feature, a useful pattern is to implement the behavior once in EngineScene and then expose it from the editor, Lua, or scene format as needed. That avoids separate implementations drifting apart.

5. OpenGL and libepoxy

The app creates a GTK GtkGLArea requesting an OpenGL 3.2 context with a depth buffer. <epoxy/gl.h> supplies OpenGL declarations and runtime function dispatch. The engine uses GLSL 1.50 shaders, vertex array objects, vertex/index buffers, and textures.

Renderer flow

  1. onOpenGlRealize() calls gtk_gl_area_make_current(), reports context errors, then calls EngineScene::initializeOpenGl().
  2. Initialization compiles and links the vertex/fragment shaders and creates cube and grid geometry. A failure returns false with an error message.
  3. onOpenGlRender() passes viewport dimensions, camera state, selected object, and optional vertex selection to EngineScene::render(). The renderer constructs view/projection/model transforms, clears color/depth buffers, then draws the floor grid and scene geometry.
  4. Cube draw calls use the scene object's color. Model meshes use imported vertex attributes, indices, base color and optional base-color texture. Mesh buffers and textures are uploaded lazily when first drawn.
  5. EngineScene::addPolygon() sends EngineVar::Polygon data through Rendering/EngineVarMeshRenderer. The adapter reads each edge's first vertex, preserves UVs and supplied normals, generates a face normal when needed, and triangulates the ordered vertices as a fan. The resulting mesh is rendered through the same indexed model path.
  6. The vertex shader applies the model-view-projection matrix. The fragment shader samples a texture when present and applies a basic fixed-direction diffuse light, except for the unlit grid.
  7. During window shutdown, onDeleteWindow() makes the context current and asks the scene to release GPU objects. clear() queues model meshes whose GPU resources should be disposed on the next render or release operation.

Viewport navigation and editing

  • The camera state is an EngineCamera with world position, yaw, and pitch. While the 3D View has focus, W/S move along the horizontal view direction, A/D strafe, E rises, and Q descends. Right-button drag changes yaw and clamped pitch.
  • Left-click calls EngineScene::pickObject(), which builds a screen ray and intersects approximate world-space bounding spheres. It supports cube and imported-model selection but is not exact triangle picking.
  • Object Explorer, Resources, and Properties each sit in their own GTK 3 GtkHandleBox; drag the panel grip to detach a panel into a separate window.
  • The Properties gizmo applies fixed axis steps: 0.25 world units for Move, 5 degrees for Rotate, and 0.1 for Scale. Cube vertex mode exposes eight local corners and draws point handles; the chosen vertex position is edited numerically.
  • Cube drawing substitutes the editable local corner positions into the cube triangle list and recomputes face normals. Edited coordinates are persisted as v0x through v7z XML attributes; absent attributes retain the original cube geometry.

Cube transforms compose translation, Z/Y/X Euler rotations, and scale. The renderer's matrix helpers are column-major. Imported node transforms use glTF translation/quaternion/scale or a matrix; animation updates the node transform relative to its imported base transform.

Safe place to add drawing

Keep OpenGL calls in src/Engine/Engine.cpp rendering/resource methods. Keep source-geometry conversion in src/Rendering/. A new mesh attribute must be wired through all three stages: EngineVertex data, buffer layout/attribute setup, and the shader inputs.

// Example pattern inside a render method, with the GtkGLArea context current:
glUseProgram(shaderProgram);
glBindVertexArray(mesh.vertexArray);
glDrawElements(GL_TRIANGLES,
    static_cast<GLsizei>(mesh.indices.size()),
    GL_UNSIGNED_INT, nullptr);
glBindVertexArray(0);

Do not call the example from an arbitrary GTK callback unless that callback first has the correct GL context current. In the current design, draw calls belong in EngineScene::render().

6. GLB model import

GlbImporter.h offers two loadGlb() overloads: one returns mesh data only; the other returns the complete EngineModelData, including nodes and clips. EngineScene::importGlb() uses the full model form, creates an EngineObject, stores the model's source path, and adds its meshes to the scene.

The importer in GlbImporter.cpp reads the GLB 2 binary header and JSON/BIN chunks, decodes accessors from buffer views, visits the selected scene's node tree, and maps primitive data into engine meshes. It can read the BIN chunk, external buffer/image paths, and base64 data URIs. GdkPixbuf decodes image bytes into RGBA pixels.

  • Only triangle primitives are emitted. POSITION is required; NORMAL and TEXCOORD_0 are optional. Missing normals are generated from triangles; missing indices are generated sequentially.
  • Supported accessor shapes are SCALAR, VEC2, VEC3, and VEC4. Component data includes common signed/unsigned integer types and float, with normalized integer conversion and buffer-stride/range checks.
  • It reads PBR base-color factors and base-color textures; other vertex attributes and material maps are not wired into the renderer.
  • The implementation rejects sparse accessors and accessors without buffer views. It limits GLB files to 512 MiB, images to 8192 pixels per side and 64 megapixels, and rejects required extensions it does not support.

Where to extend import support

  1. Accessor layout and decoding live in readAccessor() and its component conversion helpers.
  2. Primitive attributes, indices, generated normals, and base-color materials are handled in loadPrimitive().
  3. Image/buffer URI resolution and GLB chunk validation are in the main loadGlb() flow.
  4. Hierarchy traversal and animation parsing populate EngineModelData.
  5. If a new attribute or material is imported, add its representation to Engine.h and make the renderer in Engine.cpp consume it too. Importing data alone will not make it visible.

7. Model animation

Each imported clip contains samplers and channels. A channel targets a node and one of translation, rotation, or scale. The frame timer calls EngineScene::updateAnimations(deltaTime); the engine advances the selected clip, wraps time at the clip duration, samples each channel, and composes animated node transforms for rendering.

  • setAnimation() selects a valid clip and resets its time.
  • setAnimationPlaying() toggles advancement.
  • setAnimationTime() clamps the requested position into the clip interval.
  • STEP holds the prior sample. LINEAR interpolates values; rotations are normalized after component-wise interpolation. CUBICSPLINE uses Hermite interpolation and tangents.
  • Animation channels that require matrix animation are unsupported; weight/morph channels are not applied. This is distinct from static node matrices, which can be imported.

The inspector UI in main.cpp lists clips, toggles Play/Pause, and changes time with a slider. Use the existing engine methods rather than editing node data from GTK code.

8. XML scene files

SceneDocument.cpp converts the editable scene into a compact XML document. The root must be <scene version="1">; each object is a cube or a model and stores name, transform, and RGB color. Cubes also store their eight local vertices; older files without vertex attributes load with default corners. A model also stores a GLB source path, made relative to the XML file's directory when possible.

<scene version="1">
  <object type="cube" name="Floor"
          x="0" y="-1" z="0" rx="0" ry="0" rz="0"
          sx="8" sy="0.2" sz="8" r="0.25" g="0.65" b="0.95" />
  <object type="model" name="Prop" source="models/prop.glb"
          x="2" y="0" z="1" rx="0" ry="45" rz="0"
          sx="1" sy="1" sz="1" r="0.25" g="0.65" b="0.95" />
</scene>

Loading parses and validates the supported elements and finite numeric attributes, caps input at 8 MiB, resolves model sources relative to the scene path, and pre-validates model files before replacing the current scene. Missing numeric attributes use defaults (zero position/rotation, unit scale, and the default blue color). Saving escapes XML attribute text and writes numbers with enough precision for float round trips.

To add a persistent property, update the scene entry/defaults, XML parse and save paths, and then apply the property through the relevant EngineScene API. Add round-trip coverage in tests/SceneDocumentTest.cpp.

9. SDL2 controller and input service

SDL is used in InputService for GameController devices. GTK supplies the editor's keyboard/mouse events and forwards them to the same service, so scripts query one consistent API rather than handling native events themselves.

  • initialize() starts SDL's game-controller subsystem and enables controller events; poll() pumps SDL, detects disconnection, opens a recognized controller, and updates button state.
  • Keyboard and mouse hold-state sets persist until release. Separate "pressed this frame" sets capture transitions and are cleared by finishFrame().
  • Keyboard actions map W/A/S/D and arrows to movement, Space to jump, Enter to confirm, and Escape to cancel.
  • Gamepad movement uses the left stick and D-pad. A jumps, Start confirms, and B cancels. Stick axes are normalized with a dead zone.
  • axis("move_x") and axis("move_y") combine keyboard and left-stick values and clamp the result to -1..1. Up/forward is positive move_y.
  • clearKeyboard() and clearMouse() are called on focus loss so a key or button does not remain stuck when the window stops receiving events.

When adding an action, update GameAction, the keyboard mapping, the controller mapping, and the string-based isDown() mapping. Add corresponding Lua bindings only if scripts should be able to query it. For a new axis, extend InputService::axis().

10. Lua 5.4 scripting

LuaRuntime owns a lua_State and references the editor's scene and input service. It explicitly opens base, table, string, math, and UTF-8 libraries; it removes dofile and loadfile, and does not open Lua's separate io, os, package, or debug libraries.

Native C++ functions are installed in two global tables:

Lua tableAvailable functions
engineclear_scene(), add_cube(name, x?, y?, z?), set_position(id, x, y, z), set_rotation(id, x, y, z), set_color(id, r, g, b)
inputis_down(action), axis(name), gamepad_connected(), getkeypressed(key)/get_key_pressed(key), is_key_down(key), getgamepadpressed(button)/get_gamepad_pressed(button), is_gamepad_down(button), mouse position functions and mouse pressed/down functions (both compact and snake-case aliases where registered).

A script may define update(delta_time). runFile() clears the scene and prior update function, loads and executes the file, then detects whether the script defined a new update function. Every frame the editor calls update() with seconds since the previous tick. A Lua error is returned to the editor and stops further update calls.

engine.clear_scene()
local cube = engine.add_cube("Mover", 0, 0, 0)
local x = 0

function update(delta_time)
    if input.is_down("right") then
        x = x + 2 * delta_time
    end
    if input.is_down("left") then
        x = x - 2 * delta_time
    end
    engine.set_position(cube, x, 0, 0)
end

Adding a Lua function

Each C callback receives a lua_State*. Use Lua's luaL_check* helpers to validate required arguments, use lua_push* to return values, and return the number of Lua return values. The closure stores a pointer to the relevant engine/service instance as an upvalue.

int setScale(lua_State* state)
{
    const int id = static_cast<int>(luaL_checkinteger(state, 1));
    const float x = static_cast<float>(luaL_checknumber(state, 2));
    const float y = static_cast<float>(luaL_checknumber(state, 3));
    const float z = static_cast<float>(luaL_checknumber(state, 4));
    if (!getScene(state).setScale(id, x, y, z))
        return luaL_error(state, "set_scale: unknown object id %d", id);
    return 0;
}

// In LuaRuntime's constructor, while the engine table is on the stack:
registerSceneFunction(state_, scene_, "set_scale", setScale);

To implement that example, add the callback in LuaRuntime.cpp, register it in the existing engine table, and make sure EngineScene::setScale() is the authoritative operation. Update the Lua API documentation/example when changing what scripts can call.

Security note: restricting standard libraries reduces accidental access, but does not automatically make arbitrary Lua scripts a secure sandbox. Audit newly exposed native functions and any new filesystem, process, or network access.

11. SDL2_mixer audio

Audio is initialized in main(). Puppy3D initializes SDL audio, sets the FluidSynth SoundFont path if res/sf2/gm.sf2 exists, asks SDL2_mixer to initialize MIDI support, and opens a 44.1 kHz stereo output device. Audio or MIDI can be unavailable without preventing the rest of the editor from starting.

updateProperties() enables Play Audio for recognized WAV, OGG, MP3, FLAC, OPUS, and MIDI extensions when the required backend is available. The play callback frees any previously loaded music, loads the selected path with Mix_LoadMUS(), and starts it with Mix_PlayMusic(). Stop halts playback. Window destruction halts and frees music, closes audio, quits mixer support, and then shuts SDL down.

// Existing playback pattern from main.cpp:
Mix_Music* music = Mix_LoadMUS(path.c_str());
if (!music) {
    // Report Mix_GetError() through the application's normal error/status path.
} else if (Mix_PlayMusic(music, 0) == -1) {
    Mix_FreeMusic(music);
    music = nullptr;
}
// On cleanup: Mix_HaltMusic(); Mix_FreeMusic(music); Mix_CloseAudio();

If adding effects rather than background music, use SDL2_mixer's chunk API (Mix_Chunk) and track/free chunks just as carefully. Keep library initialization and cleanup paired; report Mix_GetError() instead of silently treating a failed load/play as success.

12. Build and dependency wiring

The Makefile recursively compiles every src/**/*.cpp file as C++17, so implementation modules can live in feature subfolders. It asks pkg-config for compile/link flags for GTK 3, SDL2_mixer, Lua 5.4, and epoxy. OpenGL's platform link library is added separately: opengl32 on Windows and pkg-config's gl on Linux.

make
make test
make clean

When adding a library, update its platform package installation instructions as well as the Makefile's pkg-config flags or link library. The application binary is written to export/windows/bin/ or export/linux/bin/, and export-resources copies res/ beside it.

GoalTypical files and steps
Add a scene propertyAdd storage to EngineObject in Engine.h; add/validate a setter in Engine.cpp; expose it in the GTK inspector and/or Lua; serialize it in SceneDocument.cpp; add persistence tests.
Add a renderable attributeExtend EngineVertex or EngineMesh; decode it in GlbImporter.cpp; update GPU attribute setup and GLSL in Engine.cpp; validate with a model that uses it.
Add a Lua engine commandImplement a checked Lua C callback in LuaRuntime.cpp, register it in the engine table, and route it to an EngineScene method. Update the example/API section in this guide.
Add a keyboard/gamepad actionExtend GameAction, keyboard mapping, controller mapping, string action mapping, and a Lua test/example if scripts need it.
Add a persistent scene featureExtend parse state/defaults, XML read/write, and object application in SceneDocument.cpp; cover save-load round trips in tests/SceneDocumentTest.cpp.
Add an editor controlCreate it in buildWindow(), connect a GTK callback, keep it synchronized with engine state, and queue a GL redraw after visible scene changes.

After a code change, build with make; use make test for scene-document and importer integration tests. For a rendering change, also run the editor and inspect the 3D view because ordinary scene serialization tests do not exercise a real GL context.

14. Current scope and limitations

  • Only cube corner vertices are editable. Imported GLB vertices and topology are read-only; picking uses approximate bounds rather than triangle intersections.
  • EngineVar polygons are rendered as triangle fans from their ordered edge starts; this is suitable for convex polygons, while concave polygon triangulation is not implemented. Generated polygons are transient and are omitted from version 1 XML scene saves.
  • The renderer is a prototype: a fixed directional diffuse light and base-color texture/factor, not a complete physically based renderer.
  • GLB extensions, sparse accessors, skinning, morph targets, Draco compression, additional material maps, and non-triangle primitives are not supported.
  • Only translation, rotation, and scale animation channels are evaluated. Skeletal deformation and morph weights are not applied.
  • Lua has a deliberately small opened library set, but additions to the native API need the same validation and error handling as C++-facing inputs.
  • Scene format version 1 currently records objects and their transforms/colors/source paths; it does not save animation playback state or arbitrary editor state.

These are implementation boundaries, not just UI omissions. A feature advertised in the editor should be implemented across the data model, importer/persistence path as relevant, renderer, and tests.

Source files are the final authority if this guide and code ever disagree. Keep this guide updated when changing public engine or scripting behavior.
